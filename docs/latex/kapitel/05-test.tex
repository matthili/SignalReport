\section{Test}
\label{sec:test}

\subsection{Teststrategie}
Die Teststrategie umfasste:

\begin{itemize}
    \item \textbf{Unit-Tests}: Für die Kernkomponenten (z. B. Statistik-Berechnung, Config-Handling, Measurer-Interface)
    \item \textbf{Integrationstests}: Für die Datenbankanbindung und API-Endpunkte
    \item \textbf{E2E-Tests}: Für das Web-Interface und PDF-Export
    \item \textbf{Manuelle Tests}: Für UI-Interaktionen und Benutzerfreundlichkeit
\end{itemize}

\subsection{JUnit-Testabdeckung}
SignalReport wurde mit JUnit 5 umfassend getestet. Die 22 Testklassen mit laufenden Tests -- in Paketen, die die Quellstruktur spiegeln (\texttt{config}, \texttt{measurement}, \texttt{network}, \texttt{storage}, \texttt{report}, \texttt{web}, \texttt{i18n}) -- mit insgesamt 168 Tests (zuzüglich zweier netz- bzw.\ PDF-gebundener Smoke-Klassen, die per Umgebungsvariable aktivierbar sind) decken folgende Bereiche ab:

\begin{itemize}
    \item \textbf{MeasurementTest} (5 Tests): Grundlegende Objekt-Erstellung und Validierung
    \item \textbf{HostIdentifierTest} (4 Tests): Stabile Host-Identifikation über Neustarts
    \item \textbf{StatisticsTest} (8 Tests): Mathematisch korrekte Berechnung von 95. Perzentil, Jitter und Paketverlust mit realen DB-Abfragen
    \item \textbf{ConfigTest} (18 Tests): Laden/Speichern von Konfiguration, hashPassword, Auth-Verifikation, Theme, Save+Reload, Standardwerte und Aktualisierung der Daten-Aufbereitung
    \item \textbf{H2MeasurementRepositoryTest} (13 Tests): Vollstaendige Datenbank-Integration mit IP-Tracking, Host-Registrierung, Messrunde als eine Transaktion (\texttt{saveAll}), Nebenkanal mit eigenen Verbindungen (sieht und schreibt dieselben Daten, schließt unabhängig)
    \item \textbf{HttpMeasurerTest} (3 Tests): HTTP-Messung gegen einen echten lokalen Server -- 200, 302, 403, 404 und 503 zählen als erreichbar, verweigerte Verbindung als Fehlschlag, Fehlergründe benannt
    \item \textbf{MeasurerInterfaceTest} (6 Tests): Interface-Implementierung, Polymorphie, reale Messungen (Ping/DNS/HTTP)
    \item \textbf{MaintenanceWindowTest} (7 Tests): Deaktiviert, ganztägig, aktuelle Zeit, Mitternachtsübergang, Standardwerte
    \item \textbf{SessionManagerTest} (19 Tests): Nonce-Generierung und -Validierung (Single-Use, Ablauf), Session-Erstellung und -Timeout (24\,h), Rollen\-unter\-schei\-dung (Admin/User), Challenge-Response-Verifikation, Replay-Schutz
    \item \textbf{I18nTest} (10 Tests): Schlüssel-Parität aller neun Sprachdateien gegen die Referenz (de.json), Existenz aller im Quellcode verwendeten Platzhalter (inkl. \texttt{app.js}), Fallback-Verhalten, Sprach-Erkennung
    \item \textbf{GatewayDiscoveryTest} (15 Tests): Traceroute-Parsing, RFC-1918-Klassifizierung, Gateway-Kette (nah/fern), Erkennung virtueller Gateways (Docker-Bridge, VM-NAT) und Überspringen der Docker-Bridge
    \item \textbf{ConnectivityAssessmentTest} (8 Tests): Schuld-Verdikt (Router / Internet-Gateway / Internet) auf Basis des Paketverlusts je Segment
    \item \textbf{ReliabilityReportTest} (13 Tests): lückenbewusste Verfügbarkeit/Abdeckung/MTBF/MTTR, Aggregation aufeinanderfolgender Fehlmessungen zu einem Ausfall, Ausschluss via \texttt{excluded}-Spalte, Auswertung aus Stundenwerten (\texttt{computeFromAggregates}) deckungsgleich mit der Rohdaten-Rechnung
    \item \textbf{ServiceReachabilityConfigTest} (8 Tests): Defaults (deaktiviert, 6-Stunden-Takt), Intervall-Grenzen, Pro-Dienst-Schalter, JSON-Round-Trip
    \item \textbf{ServiceReachabilityAssessmentTest} (15 Tests): Verdikt-Klassifizierung (erreichbar / Dienst-Störung / DNS-, TCP-, SNI-Sperre / Sperrseite) aus synthetischen Beobachtungen
    \item \textbf{ServiceReachabilityReportTest} (4 Tests): Verdichtung der Prüfungen zu Episoden (die Sperr-/Störungs-Timeline)
    \item \textbf{ServiceReachabilitySchedulerTest} (5 Tests): Leitungs-Gate-Entscheidung (nur erfolgreiche PING-/HTTP-Messungen zählen als Internet-Beleg)
    \item \textbf{ServiceCheckRepositoryTest} (3 Tests): \texttt{service\_checks}-Persistenz, Zeitraum-Abfrage, neueste Prüfung je Dienst
    \item \textbf{ServiceReachabilityRoutesTest} (2 Tests): \enquote{Jetzt prüfen}-Endpoint inkl.\ Abkühlphase (gegen echten Javalin-Server)
    \item \textbf{SystemRoutesTest} (2 Tests): lokaler Stopp-Endpoint (gegen echten Javalin-Server) und Loopback-Erkennung (IPv4/IPv6-Literale, keine Hostnamen-Auflösung)
    \item \textbf{StopCommandTest} (3 Tests): Stopp-Kommando \texttt{signalreport.jar stop} beendet eine laufende Instanz über den Endpoint; Randfälle \enquote{keine Instanz} und \enquote{keine Konfiguration}
    \item \textbf{DatabaseRebuilderTest} (4 Tests): Neuaufbau mit echten H2-Dateien -- Vereinigung von Primary und Shadow inkl.\ \texttt{excluded}-Flag, Übernahme der Stundenwerte und der Wasserstandsmarke, Stunden-Fallback bei simuliert unlesbarem Tag, Dateitausch mit Quarantäne und Shadow-Kopie, Marker-gesteuerter Neuaufbau beim Repository-Start, Abbruch ohne lesbare Quelle
    \item \textbf{RebuildCommandTest} (1 Test): Pfad-Fallback des Kommandozeilen-Neuaufbaus ohne Konfiguration
    \item \textbf{DataPrepConfigTest} (10 Tests): Zeitfenster (einfach, über Mitternacht, Start = Ende), Umschaltung auf das Maintenance-Fenster mit Rückfall, Begrenzung der Aufbewahrungsfrist (7--3650 Tage, 0 = nie), Begrenzung von Stunde/Minute, JSON-Round-Trip
    \item \textbf{DataPrepSchedulerTest} (5 Tests): Entscheidung \enquote{voller Lauf einmal pro Tag im Fenster}, Obergrenze außerhalb des Fensters, voller Lauf gegen echte H2-Datei inkl.\ Status und Fortschritt, manueller Start mit Abkühlphase, sofortige Abweisung eines zweiten Starts während ein Lauf aktiv ist (keine blockierende Sperre)
    \item \textbf{RollupServiceTest} (12 Tests): Stundenstatistik ohne DB (Min/Ø/Median/P95/Max/Jitter; Fehlschläge und ausgenommene Messungen), Verdichtung nur abgeschlossener Stunden, Wasserstandsmarke und Stundenlimit, ausstehende Stunden und Fortschrittsmeldung, Wiederholbarkeit (\texttt{MERGE}), Heatmap aus Stundenwerten plus Rohrest, Aufbewahrungsregel (Funde, Ausfall-Ende, ausgenommene Messungen und Wartungs-Marker bleiben; nur verdichtete Stunden; Tageslimit pro Lauf)
    \item \textbf{ExportRoutesTest} (7 Tests): gestreamter CSV-Export, Typfilter, Parameterfehler, \enquote{alle Daten} als ZIP mit genau einer CSV-Datei, Stundenwerte-CSV (gegen echten Javalin-Server), CSV-Escaping und Zeilenformat
\end{itemize}

Alle Tests laufen ohne externe Abhängigkeiten (H2-Datenbankdateien unter \texttt{data/test-*} für Integrationstests) und sind in wenigen Sekunden durchführbar.

\subsection{Beispiel-Test für Statistik-Berechnung}
\begin{lstlisting}[language=Java, caption=Test fuer 95. Perzentil]
@Test
void testP95CalculationWithSortedLatencies() {
    // Arrange: 20 Messungen (95. Perzentil = 19. Wert)
    List<Double> latencies = new ArrayList<>();
    for (int i = 1; i <= 20; i++) {
        latencies.add((double) i * 10); // 10, 20, 30, ..., 200
    }

    // Act: 95. Perzentil = Index 18 (0-basiert) = 190.0
    int p95Index = (int) Math.ceil(latencies.size() * 0.95) - 1;
    double p95Value = latencies.get(p95Index);

    // Assert
    assertEquals(18, p95Index, "Index fuer 95. Perzentil muss 18 sein");
    assertEquals(190.0, p95Value, 0.01, "95. Perzentil-Wert muss 190.0 sein");
}
\end{lstlisting}

\subsection{Test-Philosophie und -Qualität}
SignalReport verwendet eine gezielte Test-Strategie:
\begin{itemize}
    \item \textbf{Kernfunktionalität priorisiert}: Tests fokussieren auf kritische Geschäftslogik (Statistik-Berechnung, IP-Tracking, Measurer-Polymorphie), nicht auf Debug-Hilfen wie \texttt{toString()}
    \item \textbf{Realistische Szenarien}: Tests simulieren echte Nutzung (z. B. IP-Wechsel mit korrekter Zeitreihen-Sortierung, Wartungsfenster über Mitternacht)
    \item \textbf{Wartbarkeit}: Tests vermeiden fragile Assertions (z. B. exakte String-Formate) zugunsten stabiler, aussagekräftiger Prüfungen
    \item \textbf{100\% Bestehensquote}: Alle 168 automatisierten Tests laufen reproduzierbar grün -- nachweisbare Qualität für die Prüfung
\end{itemize}
